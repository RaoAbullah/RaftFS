The Real-World Problem

Why traditional centralized architectures fail in production environments

💥
Single Point of Failure
Centralized storage servers (monoliths) bring entire applications down when hardware crashes or reboots.
🧠
Split-Brain Hazard
Naive multi-server setups risk accepting conflicting writes during network partitions, corrupting data.
⏳
Sequential Bottlenecks
Searching through gigabytes of documents sequentially on a single CPU core freezes web applications.

The Solution: Raft Consensus Protocol

Guaranteed Strong Consistency ($CP$) and automated fault recovery

  • Leader Election: Randomized election timeouts ($1500\text{ms} - 3000\text{ms}$) prevent split votes and guarantee exactly one coordinator.
  • Log Replication: State transitions (file writes/deletes) are broadcast via AppendEntries RPCs.
  • Strict Quorum Majority: Writes only commit when confirmed by: $$\text{Quorum} = \lfloor N/2 \rfloor + 1$$
  • Safety Invariant: Nodes with out-of-date logs are mathematically barred from winning leadership elections.
// Raft Quorum Check in RaftFS const majority = Math.floor(totalNodes / 2) + 1; const isQuorumReached = acknowledgedFollowers >= majority; if (isQuorumReached) { this.commitIndex = this.log.length - 1; this.docStore.saveDocument(meta, content); // Replicated safely to disk! }

Decoupled Dual-Port Node Architecture

Clean separation of consensus networking from public client traffic

1. Consensus Plane (Ports 7000–7003+)

High-frequency private RPC channel solely between cluster nodes:

  • /append-entries: Periodic heartbeats & Base64 document payload batches.
  • /request-vote: Candidate election ballots with log completeness checks.
2. Client / Storage Plane (Ports 5000–5003+)

Public REST endpoints for application traffic & monitoring:

  • /api/documents/upload: Replicated write pipeline.
  • /api/search: Local Map query execution.
  • /api/status: Real-time telemetry (Term, role, storage).

Distributed Document Replication Lifecycle

How a file travels from client drag-and-drop to persistent disk quorum

Step 1: Ingestion & Hash

Cluster Gateway routes file to active Leader 👑. The Leader computes a SHA-256 checksum to ensure data integrity.

Step 2: AppendEntries RPC

Leader wraps payload into a DocUpload log entry and broadcasts it to all active follower nodes in parallel.

Step 3: Quorum Commit

Once $\ge 2/3$ nodes confirm receipt, the entry is committed to isolated disk folders (storage/node_X/).

Distributed MapReduce Search Engine

Executing parallel text queries across decentralized storage shards

Phase 1: Parallel Map Broadcast

When a search query is submitted, the coordinator simultaneously broadcasts the query string to all live nodes.

Each node parses its local files in parallel, scanning lines and extracting match snippets.

Phase 2: Aggregated Reduce

The coordinator collects incoming match streams, eliminates redundant replica occurrences, and measures end-to-end latency.

Elastic Dynamic Scaling (Membership)

Runtime cluster expansion and contraction without downtime

➕ Scale-Up (Add Storage Node)
  • Spawns a new independent Node process dynamically (e.g. Node 3 on Client :5003 / Raft :7003).
  • Broadcasts updated membership list to existing nodes over /api/cluster/update-members.
  • New node joins the 3D ring, receives heartbeats, and joins the consensus quorum!
➖ Scale-Down (Remove Node)
  • Safely shuts down the child process.
  • Purges the node from active cluster topology.
  • Automatically recalculates the majority quorum requirement $\lfloor N/2 \rfloor + 1$.
